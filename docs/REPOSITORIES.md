# Custom repositories on GitHub

PackTune can connect any number of GitHub repositories as sources of custom applications, next to the SharePoint package store. A repository holds apps with all their versions in the layout and manifest format of the store. Apps from a repository deploy as Win32 apps exactly like custom applications; the notes of the Intune app record where they came from (`repo=<owner/name>;commit=<sha>;by=<approver>`).

Design and decisions: `docs/plans/custom-repositories.md`. Template: `docs/repository-template/`.

## Set up your own repository

1. **Create the repository from the template.** Run `New-PackTuneRepositoryTemplate -Destination C:\work\my-packages -Name "Contoso packages"` (it copies `docs/repository-template/` and runs `git init`; it creates nothing on github.com). Then create the repository yourself, private unless the content is meant to be public:
   `gh repo create <owner>/<name> --private --source C:\work\my-packages --push`
   or use the website and push the folder.
2. **Protect the default branch** (Settings > Branches > Add rule): require a pull request and at least one approval, require review from Code Owners (edit `.github/CODEOWNERS`), block force pushes, require the status check "Validate PackTune repository". Whoever can push to the repository can publish software to your devices: give write access only to Intune administrators.
3. **Create a read token.** GitHub > Settings > Developer settings > Fine-grained personal access tokens: resource owner = your account or organization, **only this repository**, permission **Contents: Read-only**, an expiry date. For an organization with SSO, authorize the token for the organization. A public repository needs no token.
4. **Connect it in PackTune:** Settings > Repositories > address `owner/name`, paste the token, tick "This is our own repository" for your own repository, Add. The repository is pinned by owner/name and its numeric id. The token is stored encrypted for your Windows user (DPAPI), never in the settings file, logs or Intune notes.
5. **Put apps there.**
   - Move an existing custom application: Settings > Repositories > grant write access (a second token with **Contents: Read and write** on that repository, asked only for this step), pick the app, Move to repository. See below.
   - Or by hand: follow the layout, then run `./tools/Check-PackTuneRepository.ps1 -Path .` in your clone (same checks as PackTune, also run by the workflow on every pull request).
6. **Approve every new version** before it can be deployed (Review and approve). The dialog shows the repository (third-party label for foreign public repositories), the commit (sha, author, date, message, signature state), every file with size and SHA256, and what changed against the last approved version.
7. **Deploy** the approved version (Deploy to Intune). The app appears in Custom applications with its repository in the notes.

Rotate a token: create a new one, remove the repository in PackTune (this deletes the stored token) and add it again, then revoke the old token at GitHub. Rename or transfer the repository: PackTune notices (same repository id, new name) and asks you to confirm the new identity; a different repository behind the old name is refused.

## Layout

```
packtune.json                              index: format 1, name, apps[] (id, name, publisher, kind, versions[])
apps/<app-id>/<version>/
    package.intunewin | package.msix      the package
    installer.zip                          original installer files (stored with every version)
    recipe.json                            how it was built (data only, never executed)
    signing.cer                            public certificate of that version (msix)
    documentation.zip                      optional
    manifest.json                          SHA256 and size of every file (same format as the store)
```

Files over 90 MB are attached to a release named `<app-id>/<version>` with the same file name (GitHub allows 2 GB per asset); `manifest.json` still lists them and the index version lists them under `assets`. A version above 2 GB is not possible.

## What PackTune verifies

- The index is only a listing. The manifest of a version must match the hash in the index (and, for a deployed app, the hash in the Intune notes); every file must match the manifest in size and SHA256. A repository whose index disagrees with a manifest is refused as damaged. Path segments are validated (no `..`, no separators), `installer.zip` is unpacked zip-slip safe and only after everything matched.
- A new version, or any change of a manifest, is not deployable until you approved exactly that manifest hash. A repository can additionally require verified (signed) commits; an unverified commit then cannot be approved. Approval can not be switched off.
- Nothing from a repository is executed on the admin PC. Device scripts are generated by PackTune from data it read itself (the MSI properties, the identity of the signed MSIX); recipe arguments must be simple `PROPERTY=value` pairs.
- Only HTTPS to GitHub hosts; redirects to other hosts are refused and the token is never sent to a download host. Rate limits are handled with `Retry-After` and an ETag cache; without a token GitHub allows 60 requests per hour, and PackTune says so when that is not enough.
- **Certificates from a repository are never trusted.** An MSIX of a repository is re-signed on this computer at deploy time with a new single-use, non-exportable certificate whose subject equals the package's Publisher exactly (the package family stays, updates keep working), with a mandatory timestamp; the key is deleted right after signing. Only the new public certificate goes into the Win32 wrapper (`signing.cer` of the repository is not used). Every certificate that goes into TrustedPeople (also checked again on the device) must be a self-signed leaf, CA=false, Code Signing only, subject = publisher. The Intune notes record `thumb=` (new) and `origthumb=` (original signer). A publisher that is not a simple `CN=...` subject is refused.
- **"Verified commit"** only means GitHub saw a signature of the committer's own key. Set allowed signers per repository (`-AllowedLogins` / Settings): author and committer of the version's commit must both be on the list, otherwise it cannot be approved. The approval dialog shows both logins and the list.
- Downloads are limited to the size in the manifest: Content-Length is checked first and the bytes are counted while copying; a larger file is aborted and removed.
- Offline or GitHub down: the list shows the last known index as stale; nothing is deployed from a stale repository.
- The same app id in two repositories stays two separate sources; deploying from one never updates from the other.

## Move to repository

Copies every version of a custom application from the package store into a repository you own and verifies it:

1. All versions must be complete in the store and have an Intune app with the full manifest anchor (otherwise nothing vouches for them: the move is refused with the way out).
2. Per version: download from SharePoint (verified against its manifest and the Intune anchor), one commit per version with the files and the updated index; big files as release assets. The manifest is copied byte for byte, so the Intune anchor stays valid.
3. Read everything back from the repository and compare hashes. Any mismatch stops here; nothing is removed.
4. The notes of the Intune apps get `repo=` and `commit=` (the anchor is untouched); export and edit read from the repository from then on.
5. SharePoint is kept. Only when you confirm the list of what would be removed is the store folder deleted (SharePoint keeps it in its recycle bin for 93 days; the repository keeps the history). Running Move again continues: identical versions are skipped.

Third-party (foreign public) repositories are read only and never a Move target.

## Command line

`Add-PackTuneRepository`, `Get-PackTuneRepositories`, `Get-PackTuneRepositoryApps`, `Get-PackTuneRepoApprovalRequest`, `Approve-PackTuneRepoVersion`, `New-PackTuneRepoApp`, `Grant-PackTuneRepoWrite`, `Move-PackTuneCustomAppToRepository`, `Confirm-PackTuneRepositoryIdentity`, `Remove-PackTuneRepository`, `New-PackTuneRepositoryTemplate`, `Test-PackTuneRepositoryClone` (alias `Check-PackTuneRepository`).
